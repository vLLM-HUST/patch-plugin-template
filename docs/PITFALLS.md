# 踩坑与经验

来自把真实 PR 抽成运行时插件的几次实践。每条都是实际出过问题的。

## 1. "启用"不等于"安装"
`vllm-hust-ext extension enable <id>` 只把状态记成 `enabled`。插件默认是 no-op,必须在**启动 vLLM 的
环境里**导出 `VLLM_HUST_<NAME>_ENABLE=1` 才会安装。判断办法:日志里要有 `installed` 事件,没有就是没装。

## 2. "安装"不等于"生效"
类属性被替换了,不代表替换后的代码被调用过。每个进程第一次真正走到替换代码时输出一条
`runtime_effective`,并带 `pid`。**压测前先确认这条事件出现**,否则 ON 组其实是 OFF,白跑。

## 3. 宿主用 spawn 启动的子进程拿不到补丁
spawn 出来的是全新解释器,不会跑 vLLM 的插件加载。症状:`installed` 有、`runtime_effective` 没有、
旧代码还在跑。解决见 `src/<module>/bootstrap.py`:替换宿主的启动函数,让子进程从模块级入口
`child_entry` 开始,先 `register()` 再运行宿主原目标。`pid` 能证明子进程里补丁是否真的跑了。
直接改源码的 patch 没有这个问题,**从源码 patch 转插件时最容易漏**。

## 4. 宿主会漂移,不要套旧 diff
抽取时宿主代码可能已经变了(例如某个调用多了一个参数)。按**当前宿主源码**重写替换,并让守卫检查
容易被漏掉的细节,否则补丁会悄悄丢参数、改变行为。
注意守卫是对源码文本做**子串匹配**,注释和字符串里的同名片段也会让它通过。标记要选一个有区分度的**代码**片段,不要选可能出现在注释里的词。

## 5. 微基准会高估收益
在合成输入上测出几十倍加速,不代表真实服务里有收益。真实输入往往小得多(这个函数本来就只要几毫秒)。
**在真实服务里给各阶段分段计时**,看你优化的那一段占总耗时多少。那一段占 0.4%,再快 50 倍也只省 0.4%。
注意惰性生成器:创建时不干活,耗时发生在消费它的地方,要在每次 `next` 处累加。

## 6. 先问"能不能传导到服务层"
被优化的代码不在关键路径上(旁路进程、后台线程)时,只有当它慢到让关键路径等它,才会影响服务。
先量**关键路径被它阻塞的时间占比**,这是收益上限。占比只有 2%,就别指望吞吐能涨 10%。

## 7. 对照实验的设计
- OFF 必须是**同配置、只差开关**,不是"另一个版本"。
- 单次观测没有意义。用 ABBA 顺序重复,并**记下同一臂两次之间的差**作为噪声参照。差异小于噪声参照就是没差异。
- 只有一个指标出现好转、其他指标不同向、没有机制解释时,记为"未证实",不要写成优势。

## 8. 一个 PR 往往是几个改动打包的
逐个子机制单独测。无收益的删掉,包更小、更容易审。别整包搬运。

## 9. 差分测试
用宿主原函数的**逐字拷贝**做基准,随机生成大量输入,包括重复、缺失、空输入,要求输出完全一致,
包括容器的顺序。手挑几个用例不够。

## 10. 运维小事
- `pkill -f "vllm serve"` 会匹配到你自己的 ssh 命令行。用方括号写法 `[v]llm serve`,并且命令文本里别再出现被匹配的串。
- 只杀 `vllm serve` 会留下 `VLLM::EngineCore` 和 worker,继续占着显存。两条一起杀:`pkill -f "[V]LLM::"` 和 `pkill -f "[v]llm serve"`,然后确认没有残留再启动。
- 配置里的设备编号用容器内的逻辑编号(如 `0,1`),不是 `npu-smi` 里的物理编号。

## 11. 报告要同时写优势和局限
没有服务层收益是正常结果,如实写,并写清楚原因、证据和没验证的部分。见 `REPORT_TEMPLATE.md`。
